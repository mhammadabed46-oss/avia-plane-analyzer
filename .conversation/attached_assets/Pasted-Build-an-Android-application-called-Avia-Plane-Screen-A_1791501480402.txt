Build an Android application called:

Avia Plane Screen Analyzer

The application is a screen-monitoring and statistical-analysis tool.

Its main purpose is NOT manual data entry.

The application should monitor the user's Android screen while the Avia Plane game is running, visually detect the multiplier displayed by the game, automatically record each completed round, and continuously calculate historical statistics.

IMPORTANT:
The application must be designed as an analysis and data-recording tool only. It must NOT claim to predict the next result with certainty, guarantee profit, or automatically place bets.

━━━━━━━━━━━━━━━━━━

1. MAIN CONCEPT
   ━━━━━━━━━━━━━━━━━━

The user opens the Avia Plane game normally.

Then the user starts:

SCREEN MONITORING

The application should:

1. Monitor the screen.
2. Identify the area where the multiplier is displayed.
3. Read the multiplier using OCR / computer vision.
4. Detect when a new round starts.
5. Detect when the current round ends.
6. Capture the final multiplier.
7. Save it automatically.
8. Add it to the historical database.
9. Update statistics immediately.
10. Display the latest analysis.

The user should NOT have to type the multiplier manually.

━━━━━━━━━━━━━━━━━━
2. ANDROID SCREEN ACCESS
━━━━━━━━━━━━━━━━━━

Use appropriate Android APIs for screen capture, such as:

MediaProjection API

The application must request the necessary Android permission before monitoring the screen.

Clearly explain to the user why screen capture permission is required.

The application should not access:

- Contacts
- Messages
- Phone calls
- Location
- Microphone

unless absolutely required.

Screen monitoring must stop immediately when the user presses:

STOP MONITORING

━━━━━━━━━━━━━━━━━━
3. OCR / VISUAL RECOGNITION
━━━━━━━━━━━━━━━━━━

Use an appropriate on-device OCR/computer-vision solution.

Preferred approach:

Google ML Kit Text Recognition or another reliable Android-compatible OCR library.

The system should search the captured screen for values matching patterns such as:

1.24x
2.51x
10.32x
100.45x

The "x" may or may not be detected by OCR.

The system should therefore recognize numeric multiplier patterns even if OCR returns:

1.24
2.51
10.32

Do NOT simply read every number on the screen.

The system must attempt to identify the multiplier based on:

- Position
- Size
- Formatting
- Repeated location
- Numeric pattern
- Changes between frames

━━━━━━━━━━━━━━━━━━
4. CALIBRATION
━━━━━━━━━━━━━━━━━━

Because different phones and versions of the game may display the multiplier in different locations, create a calibration system.

When monitoring starts for the first time:

Display:

Select Multiplier Area

Allow the user to draw/select a rectangular area around the multiplier on the screen.

Save this region.

After calibration, OCR should primarily analyze this selected region instead of the entire screen.

Provide:

Recalibrate

if the user changes the game layout.

━━━━━━━━━━━━━━━━━━
5. ROUND DETECTION
━━━━━━━━━━━━━━━━━━

The application must distinguish between:

- Current multiplier
- Final multiplier
- Previous round
- New round

Do not record the same round repeatedly.

For example, if the screen displays:

1.05x
1.12x
1.25x
1.43x
1.72x
2.04x
2.31x

these are NOT seven different rounds.

They represent one round.

The application should save only the final multiplier when the round ends.

Example:

Round #105 → 2.31x

Then wait for the next round.

━━━━━━━━━━━━━━━━━━
6. DUPLICATE PROTECTION
━━━━━━━━━━━━━━━━━━

Implement strong duplicate protection.

The same multiplier must not be saved multiple times simply because the screen remained unchanged for several frames.

Use:

- Timestamp
- Value
- Screen-state change
- Round-state detection

to distinguish separate rounds.

20. ERROR HANDLING
━━━━━━━━━━━━━━━━━━

"Multiplier not detected."

If the screen changes:

"Screen layout changed — recalibration may be required."

If OCR confidence is low:

"Low confidence — waiting for clearer result."

"Screen monitoring permission is required."

The application should never silently create fake results.

23. PERFORMANCE
━━━━━━━━━━━━━━━━━━

The application should be optimized for Android phones.

Do not perform unnecessary full-screen OCR continuously if it can be avoided.

Once the multiplier region has been calibrated, process only that region whenever possible.

Use an efficient sampling frequency.

Avoid excessive battery consumption.

Do not save every video frame.

Only store detected results and necessary metadata.

━━━━━━━━━━━━━━━━━━

Screen images should preferably be processed locally on the device.

Do not upload screenshots to external servers.

Do not store complete screenshots unless explicitly needed for debugging and the user enables this option.

The user must always be able to stop monitoring.
